여기서 `-d` 옵션을 사용하지 않았기 때문에 애플리케이션 출력이 실시간으로 cmd에 보입니다. 보

# Dockerfile

모든 것을 도커파일에서 사직되었답니다.

> 도커가 이미지를 만들기 위해 도커파일에 있는 instruction (command)을 사용한다.
>
> 도커 엔진이 도커파일 안에 있는 명령어들을 (instruction) 일일이 실행하고 작동 가능한 이미지를 만든다.

![](/images/w4_p2/1775696157814.png)\### 도커 파일의 구조

![](/images/w4_p2/1775696417993.png)\## 도커 파일 만들기

```
vim [dockerfile name]
```

원하는 텍스트 에디터를 사용해 Dockerfile을 생성할 수 있습니다. (Dockerfile은 일반 텍스트 파일이라고 생각해도 됩니다.)

![](/images/w4_lab2/1775697312788.png)저는 개인적으로 `neovim`를 선호합니다. 지금 AI 시대, Vibe Coding 많이 하지만 vim motion 배워놓으면 언젠가 도움이 되겠죠.

```
FROM diamol/node
```

dockerfile의 첫번째 instruction은 꼭 `FROM` 이어야 된다.

> FROM – 기존에 존재하는 이미지를 베이스 이미지로 사용합니다. 즉, 이미 준비되어 있는 `diamol/node` 이미지를 기반으로 하고, 그 위에 필요한 기능을 추가한다고 생각하면 됩니다.

---

```

ENV METHOD="HEAD"
ENV INTERVAL=3000
```

`ENV` - 환경변수를 설정하는 명령어입니다.

---

```
WORKDIR /web-ping
```

컨테이너 내부의 작업 디렉토리를 설정합니다. 즉,앞으로 실행되는 모든 명령은 `/web-ping` 폴더 기준으로 실행합니다.

---

```
COPY app.js
```

`COPY` – Dockerfile과 같은 폴더에 있는 파일을 컨테이너 이미지 내부로 복사하는 명령어입니다.

---

```
CMD ["node", "/web-ping/app.js"]
```

`CMD` - 컨테이너가 시작될 때 실행될 기본 명령어를 지정하는 키워드

이 명령어는 이미지를 만들고 있는 모든 `layer`를 보여줍니다.

**Layer 가 뭐지?**

**레이어 = 파일시스템 변경 내용의 스냅샷**

각 레이어는 이전 레이어 위에 "무엇이 달라졌는지"만 기록합니다. 예를 들어 Layer 2는 Layer 1 전체를 복사하는 게 아니라 `apt-get install`로 추가된 파일들의 변경분만 담고 있어요.

**레이터가 Immutable인 이유**

한번 만들어진 레이어는 절대 수정되지 않습니다. 그래서 여러 이미지가 같은 레이어를 공유해서 재사용할 수 있고, 캐싱도 가능해집니다. `docker build` 할 때 "이미 만든 레이어는 건너뛴다"는 게 바로 이 덕분입니다.

> Dockerfile에서 파일을 추가하거나 변경하는 명령어만 레이어를 만든다(RUN, COPY, ADD, FROM). 나머지는 설정만 바꾸므로 레이어를 만들지 않는다.

## 도커파일 스크립트 최적화

> 도커파일 최적화 - 이미지 레이어를 줄이고, 캐시를 잘 활용하는 최적화 전략

#### 1. 캐시 활용

도커는 이미지를 빌드할 때 레이어를 위에서 아래로 순서대로 쌓습니다. 그런데 특정 레이어가 변경되면 그 아래 레이어들은 캐시를 무시하고 전부 다시 빌드합니다. 그래서 자주 바뀌는 것(소스 코드)은 아래에, 잘 안 바뀌는 것(dependencies 설치)은 위에 두는 게 좋습니다.

#### 2. 레이어 줄이기

`RUN` 명령어를 여러 줄 쓰면 레이어가 그만큼 많이 생깁니다. `&&`로 묶어서 하나의 `RUN`으로 합치면 레이어 수를 줄일 수 있습니다.

#### 3. 불필요한 파일 제외

`.dockerignore` 파일을 사용해서 이미지에 포함할 필요 없는 파일들(예: `node_modules`, `.git`)을 제외하면 이미지 크기가 줄어듭니다.

#### 4. 베이스 이미지 선택

`ubuntu` 같은 무거운 베이스 이미지 대신 `alpine` 같은 가벼운 이미지를 쓰면 전체 이미지 크기가 크게 줄어듭니다.

# Multi-Stage Build

멀티 스테이지 빌드란 무엇인가?

이미지를 빌드할 때 단계를 여러 개로 나누는 방법이에요.

예를 들어 Java 앱을 빌드한다고 하면, 빌드할 때는 JDK(컴파일러 포함, 무거움)가 필요하지만 실행할 때는 JRE(런타임만, 가벼움)만 있으면 되잖아요. 근데 그냥 Dockerfile 하나로 만들면 JDK가 최종 이미지에 그대로 남아서 이미지가 불필요하게 커져요.

Multi-Stage Build는 이걸 이렇게 해결해요.

```
FROM maven AS build        # 1단계: 빌드용 (무거운 JDK)
COPY . .
RUN mvn package

FROM openjdk:jre AS final  # 2단계: 실행용 (가벼운 JRE)
COPY --from=build target/app.jar .  # 1단계 결과물만 가져옴
```

최종 이미지에는 2단계만 남아요. 

1단계는 빌드할 때만 쓰고 버려지는 거예요. 덕분에 이미지 크기가 크게 줄어듭니다.

> **멀티 스테이지 빌드는 무거운 작업(빌드)과 가벼운 결과(실행)을 분리하여, 안전하고 효율적인 컨테이너를 만드는 기술이다.**

![](/images/w4_lab2/1775817552175.png)실제 예제는 위와 같습니다. 

`AS` 뒤에 오는 이름은 각 단계를 참조하기 위한 별명이라고 생각하면 됩니다.

# 마무리

이번 챕터의 핵심은 **Dockerfile을 잘 작성하는 것이 곧 효율적인 이미지를 만드는 것**이라는 점입니다.

레이어 순서 하나만 바꿔도 빌드 시간이 크게 줄어들고, Multi-Stage Build를 활용하면 최종 이미지 크기도 눈에 띄게 줄어듭니다. 단순히 동작하는 Dockerfile을 넘어서, 캐시와 레이어를 의식하며 작성하는 습관을 들이는 것이 중요합니다.
