## Introduction

클라우드 엔지니어를 목표로 한다면, AWS의 서버 개념은 반드시 이해해야 합니다
하지만 많은 사람들이 EC2, AMI, VPC 같은 개념을 **단편적으로 외우기만 하고 구조적으로 이해하지 못합니다.**

예를 들어 이런 질문에 바로 답할 수 있나요?

- EC2를 껐다 켜면 내 데이터는 사라지나요?
- Lambda와 EC2는 어떤 기준으로 선택해야 하나요?
- AMI는 그냥 OS 이미지인가요, 아니면 그 이상인가요?

이 글에서는 AWS 서버 개념을 **전체 구조 중심으로 한 번에 정리**하고, 각 서비스가 왜 존재하는지, 어떤 상황에서 써야 하는지까지 다룹니다.

## AWS 서버 개념 전체 구조

AWS는 단순한 서버 하나가 아니라, 여러 서비스가 레이어별로 조합된 구조입니다.
아래 흐름을 기억해 두면 각 서비스의 위치가 자연스럽게 보입니다.

```
사용자 요청 (User Request)
        ↓
[Compute Layer]   EC2 / Lambda / ECS / Lightsail
        ↓
[Storage Layer]   EBS / S3 / Instance Store
        ↓
[Network Layer]   VPC / Subnet / Internet Gateway
        ↓
[Security Layer]  Security Group / IAM / CloudWatch
```

각 레이어는 독립적으로 동작하지만, **함께 조합될 때 비로소 완전한 서버 인프라**가 됩니다.
이제 하나씩 뜯어봅시다.

## 1. Amazon Computing Service — 왜 클라우드를 쓰는가?

AWS의 컴퓨팅 서비스를 이해하려면, 먼저 "왜 서버를 직접 사지 않고 빌려 쓰는가"를 이해해야 합니다.

### 전통적인 온프레미스 방식의 문제

기존에는 서비스를 운영하려면 물리 서버를 구입하고, 데이터센터 공간을 임대하고, 전기/냉각 시스템까지 직접 관리해야 했습니다.
가장 큰 문제는 **트래픽 예측의 어려움**입니다.

- 평소 트래픽에 맞추면 → 피크 시간에 서버 다운
- 피크에 맞추면 → 평소에는 자원 낭비 (비용 폭증)

### 클라우드가 해결한 것

AWS는 이 문제를 **탄력적 확장(Elasticity)** 으로 해결합니다.
트래픽이 늘면 서버를 자동으로 추가하고, 줄면 자동으로 반납합니다.
비용은 **쓴 만큼만** 냅니다.

> 💡 이 개념을 "Pay-as-you-go" 모델이라고 하며, AWS의 모든 서비스에 적용되는 핵심 철학입니다.

## 2. EC2 (Elastic Compute Cloud) — AWS의 기본 서버

EC2는 AWS에서 가장 많이 사용되는 서비스로, **가상화된 서버(인스턴스)를 원하는 만큼 생성하고 제거할 수 있는 서비스**입니다.

### EC2의 핵심 특징

1. **탄력성** - 수분 내에 서버 생성/삭제 가능 
2. **다양한 OS** - Amazon Linux, Ubuntu, Windows 등 선택 가능
3. **유연한 구성** - CPU, 메모리, 스토리지를 용도에 맞게 선택 
4. **통합성** - VPC, EBS, IAM 등 다른 AWS 서비스와 긴밀하게 연동 

### EC2 인스턴스의 생명주기

EC2 인스턴스는 아래와 같은 상태를 가집니다.

```
[Pending] → [Running] → [Stopping] → [Stopped] → [Terminated]
                ↑                           |
                └──────────── Start ────────┘
```

- **Running**: 서버가 실행 중 (비용 발생)
- **Stopped**: 서버가 꺼진 상태 (EBS 비용만 발생, 재시작 가능)
- **Terminated**: 서버 완전 삭제 (복구 불가)

> ⚠️ **주의**: Stopped 상태에서도 EBS 스토리지 비용은 계속 발생합니다. 장기간 사용하지 않는 인스턴스는 스냅샷을 찍고 Terminate하는 것이 비용 절감에 유리합니다.

## 3. EC2 Instance Type — 어떤 서버를 골라야 할까?

EC2는 용도에 따라 수십 가지 인스턴스 타입을 제공합니다. 이름만 봐도 스펙을 파악할 수 있도록 규칙이 있습니다.

### 인스턴스 이름 구조

![instance_type](/images/cloud_prog_week2/instance_type.png)

### 주요 인스턴스 패밀리

1. **t** (General Purpose) - 가벼운 웹서버, (예: t3.micro, t3.small)
2. **m** (General Purpose) - 균형 잡힌 범용 워크로드 (예:  m6i.large, m6i.xlarge)
3. **c** (Compute Optimized) - CPU 집약적 연산, 게임 서버, 고성능 웹서버 (예: c6i.large)
4. **r** (Memory Optimized) - 대용량 인메모리 DB, 빅데이터 분석 (예: r6i.large)
5. **p / g** (GPU) - 머신러닝, 딥러닝, 그래픽 렌더링 (예: p3.2xlarge, g4dn.xlarge)
6. **i** (Storage Optimized) - 고속 I/O가 필요한 NoSQL DB (예: i3.large )

### 프리 티어로 연습하기

AWS 신규 계정은 **t2.micro (또는 t3.micro) 인스턴스를 월 750시간 무료**로 사용할 수 있습니다.
학습 목적이라면 이것만으로도 충분합니다.

## 4. AMI (Amazon Machine Image) — 서버의 청사진

AMI는 EC2 인스턴스를 시작할 때 사용하는 **템플릿(이미지)** 입니다.
단순히 OS만 포함하는 것이 아니라, **OS + 설치된 소프트웨어 + 설정 + 데이터**까지 통째로 담겨 있습니다.

### AMI가 포함하는 것

```
AMI
├── 루트 볼륨 스냅샷 (OS, 소프트웨어, 파일)
├── 인스턴스 타입 정보
├── 블록 디바이스 매핑 (스토리지 구성)
└── 권한 설정 (퍼블릭 / 특정 계정만 공유)
```

### AMI의 3가지 유형

1. **AWS 제공 AMI** - AWS가 공식 관리하는 이미지 (예: Amazon Linux 2023, Ubuntu 22.04)
2. **AWS Marketplace AMI** - 벤더사가 제공하는 유료/무료 이미지 
3. **커스텀 AMI** - 내가 직접 만든 이미지 (내 앱 + 설정이 포함된 이미지)

### 실무에서 커스텀 AMI가 왜 중요한가?

서버를 10대 띄워야 할 때, 매번 각 서버에 접속해서 패키지를 설치하고 설정 파일을 복사하는 건 매우 비효율적입니다.
커스텀 AMI를 만들면 **완벽하게 준비된 서버를 클릭 한 번으로 여러 대 복제**할 수 있습니다.

오토 스케일링(Auto Scaling)과 결합하면 트래픽 증가 시 동일한 AMI로 서버를 자동으로 확장할 수 있어, **무중단 서비스의 핵심 기반**이 됩니다.

> 💡 **비유**: AMI는 마치 붕어빵 틀과 같습니다. 틀(AMI) 하나만 잘 만들어 두면, 같은 모양의 붕어빵(EC2 인스턴스)을 얼마든지 찍어낼 수 있습니다.

## 5. EC2 Storage — 데이터를 어디에 저장할까?

EC2 인스턴스에는 두 가지 저장 방식이 있으며, 이 둘의 차이를 모르면 **데이터를 통째로 잃을 수 있습니다.**

### Instance Store (임시 저장소)

- 물리 서버에 직접 연결된 스토리지
- **인스턴스가 중지/종료되면 데이터가 사라짐**
- 속도가 매우 빠름 (로컬 디스크 수준)
- 임시 캐시, 버퍼, 스크래치 데이터에 적합

### EBS (Elastic Block Store, 영구 저장소)

- 네트워크로 연결되는 별도의 블록 스토리지
- **인스턴스가 종료돼도 데이터 유지**
- 인스턴스와 독립적으로 존재 → 다른 인스턴스에 재연결 가능
- 스냅샷으로 백업 및 복원 가능

```
[Instance Store]    빠르지만 휘발성 → 캐시, 임시 데이터
[EBS]               느리지만 영구적 → DB, 앱 데이터, OS
```

> ⚠️ **실수 방지**: EC2를 처음 배울 때 가장 많이 하는 실수가 인스턴스를 Terminate했을 때 데이터가 사라지는 것입니다. 중요한 데이터는 반드시 EBS에 저장하거나, 인스턴스 삭제 전에 EBS 볼륨을 분리해 두세요.

## 6. VPC (Virtual Private Cloud) — 나만의 네트워크 공간

VPC는 AWS 안에서 **논리적으로 격리된 가상 네트워크**를 만드는 서비스입니다.
쉽게 말하면, AWS 안에 "내 전용 사무실 네트워크"를 구성하는 것입니다.

### VPC의 핵심 구성 요소

```
VPC (10.0.0.0/16)
├── Public Subnet (10.0.1.0/24)   ← 인터넷 접근 가능
│       └── EC2 (웹 서버)
│       └── Internet Gateway
│
└── Private Subnet (10.0.2.0/24)  ← 인터넷 직접 접근 불가
        └── EC2 (DB 서버)
        └── RDS (데이터베이스)
```

### 주요 구성 요소 설명


1. **Subnet** - VPC를 더 작은 네트워크 구역으로 나눈 것. Public/Private으로 구분 
2. **Internet Gateway** - VPC와 인터넷 사이의 문. Public Subnet에 연결해야 외부 접근 가능 
3. **Route Table** - 트래픽이 어디로 가야 하는지 규칙을 정의 
4. **NAT Gateway** - Private Subnet의 서버가 인터넷에 나가도록 허용 (반대 방향은 차단) 
5. **Security Group** - 인스턴스 단위의 방화벽. 허용할 포트/IP를 지정 
6. **NACL** - Subnet 단위의 방화벽. Security Group보다 상위 레벨 

### 왜 Public/Private Subnet을 나누는가?

보안 때문입니다. 웹 서버는 외부에서 접근해야 하므로 Public Subnet에 두지만, DB 서버는 외부에서 직접 접근하면 안 되므로 Private Subnet에 배치합니다.
이렇게 하면 해커가 DB에 직접 접근하는 것을 네트워크 수준에서 차단할 수 있습니다.

## 7. EC2 Security & Monitoring — 서버를 어떻게 보호하는가?

### Security Group (보안 그룹)

Security Group은 EC2 인스턴스의 **인바운드/아웃바운드 트래픽을 제어하는 가상 방화벽**입니다.

```
# 웹서버용 Security Group 예시
인바운드 규칙:
  - HTTP  (80)   : 0.0.0.0/0 (전체 허용)
  - HTTPS (443)  : 0.0.0.0/0 (전체 허용)
  - SSH   (22)   : 내 IP만 허용 (예: 203.0.113.0/32)

아웃바운드 규칙:
  - 모든 트래픽 : 기본 허용
```

> 💡 Security Group은 **화이트리스트 방식** (명시적으로 허용한 것만 통과)으로 동작합니다. 아무것도 설정하지 않으면 모든 인바운드 트래픽이 차단됩니다.

### CloudWatch (모니터링)

CloudWatch는 AWS 리소스의 **메트릭을 수집하고 시각화하며, 이상 시 알림을 보내는 모니터링 서비스**입니다.

주요 기능:
- **메트릭 수집**: CPU 사용률, 네트워크 I/O, 디스크 읽기/쓰기 등
- **로그 수집**: 애플리케이션 로그, 시스템 로그를 중앙 집중 관리
- **알람(Alarm)**: 임계값 초과 시 이메일/SMS 알림 또는 자동 조치
- **대시보드**: 여러 메트릭을 한 화면에서 모니터링

예를 들어 "CPU 사용률이 80%를 초과하면 자동으로 서버를 추가 생성"하는 Auto Scaling 정책을 CloudWatch Alarm과 연동하면 완전 자동화된 인프라가 완성됩니다.

## 8. EBS (Elastic Block Store) — EC2의 하드디스크

EBS는 EC2에 연결하는 **네트워크 기반 블록 스토리지**로, 실제 하드디스크처럼 파일 시스템을 구성하고 데이터를 저장합니다.

### EBS 볼륨 타입

- **gp3** (SSD, 범용): 가격 대비 성능 우수, 현재 기본값 → 일반 워크로드, 개발 환경
- **io2** (SSD, 프로비저닝 IOPS): 고성능, 높은 IOPS 보장 → 고성능 DB (Oracle, SQL Server)
- **st1** (HDD, 처리량 최적화): 대용량 순차 읽기/쓰기에 유리 → 빅데이터, 로그 처리
- **sc1** (HDD, 콜드 HDD): 가장 저렴, 자주 접근하지 않는 데이터 → 아카이브, 백업

### EBS 스냅샷

EBS는 특정 시점의 데이터를 **스냅샷(Snapshot)** 으로 백업할 수 있습니다.
스냅샷은 S3에 저장되며, 다른 리전이나 계정으로 복사해서 재해 복구(DR)에 활용할 수도 있습니다.

```
[EBS 볼륨] ──스냅샷 생성──→ [S3] ──복원──→ [새 EBS 볼륨]
                                    └──복사──→ [다른 리전 EBS 볼륨]
```

## 9. Lambda — 서버 없이 코드를 실행한다

Lambda는 **서버를 직접 관리하지 않고 코드만 업로드하면 실행해 주는 서버리스(Serverless) 컴퓨팅 서비스**입니다.

### EC2 vs Lambda 비교

- 서버 관리: EC2는 직접 관리 (패치, 업데이트 등), Lambda는 AWS가 완전 관리
- 실행 방식: EC2는 항상 켜져 있음, Lambda는 이벤트 발생 시에만 실행
- 비용: EC2는 서버가 켜진 시간만큼, Lambda는 실행 횟수 × 실행 시간
- 최대 실행 시간: EC2는 제한 없음, Lambda는 15분
- 상태 유지: EC2는 가능, Lambda는 불가능 (Stateless)
- 적합한 워크로드: EC2는 장기 실행/지속적 트래픽, Lambda는 짧은 작업/간헐적 이벤트

### Lambda가 빛나는 상황

Lambda는 다음과 같은 이벤트 기반 아키텍처에서 매우 강력합니다.

```
[S3에 이미지 업로드]
        ↓ 이벤트 트리거
[Lambda: 이미지 리사이징 함수 실행]
        ↓
[리사이징된 이미지를 다른 S3 버킷에 저장]
```

```
[API Gateway로 HTTP 요청 수신]
        ↓ 이벤트 트리거
[Lambda: 비즈니스 로직 실행]
        ↓
[DynamoDB에 데이터 저장 후 응답 반환]
```

### 비용 절감 효과

Lambda는 **요청 100만 건당 $0.20, 실행 시간에 대한 비용**이 부과됩니다.
월 100만 건 이하 요청은 **프리 티어로 무료**입니다.

소규모 서비스나 백그라운드 처리 작업이라면 EC2보다 Lambda가 훨씬 경제적일 수 있습니다.

> 💡 단, Lambda는 **Cold Start** 문제가 있습니다. 함수가 오랫동안 호출되지 않으면 첫 실행 시 초기화 시간이 소요됩니다. 레이턴시가 중요한 서비스에서는 이를 고려해야 합니다.

## 10. ECS (Elastic Container Service) — 컨테이너를 AWS에서 운영하기

ECS는 **Docker 컨테이너를 AWS에서 실행하고 관리하는 서비스**입니다.
마이크로서비스 아키텍처를 도입할 때 핵심적으로 사용됩니다.

### 컨테이너가 필요한 이유

"내 컴퓨터에서는 잘 됐는데 서버에서 안 된다"는 문제를 해결하기 위해 Docker가 등장했습니다.
Docker는 앱 실행에 필요한 모든 것(코드, 런타임, 라이브러리, 환경 변수)을 **컨테이너** 라는 독립된 패키지로 묶습니다.

### ECS 실행 유형

- EC2 유형: EC2 인스턴스 위에서 컨테이너 실행. 인프라를 직접 관리하며 비용 절감 가능
- Fargate 유형: 서버리스 방식으로 컨테이너 실행. 인프라 관리 불필요, 간편한 배포

> ECS 외에도 Kubernetes 기반의 **EKS (Elastic Kubernetes Service)** 가 있습니다. 대규모 마이크로서비스 운영에는 EKS가 더 적합하지만 학습 난이도가 높습니다.

## 11. Lightsail — 클라우드 입문자를 위한 간소화된 서비스

Lightsail은 **복잡한 AWS 설정 없이 간단하게 서버를 시작할 수 있는 서비스**입니다.

### EC2와 Lightsail의 차이

- 대상: EC2는 중급~고급, Lightsail은 초보자/소규모 프로젝트
- 설정 복잡도: EC2는 높음 (VPC, SG 등 직접 구성), Lightsail은 낮음 (기본값으로 자동 설정)
- 가격 구조: EC2는 종량제, Lightsail은 월정액 (예: $3.5~)
- 확장성: EC2는 매우 높음, Lightsail은 제한적
- 번들 제공: EC2는 없음, Lightsail은 고정 CPU + RAM + SSD + 트래픽 포함

### Lightsail이 적합한 경우

- 개인 블로그, 포트폴리오 사이트
- WordPress, Ghost, Joomla 등 CMS 운영
- 소규모 스타트업의 MVP 서버
- AWS를 처음 배우는 학습 환경

## 서비스 선택 가이드

어떤 서비스를 선택해야 할지 헷갈릴 때 아래 흐름도를 참고하세요.

```
서버가 필요한가?
├── 아니오 → 코드만 실행? → Lambda
│                └── 컨테이너? → ECS (Fargate)
│
└── 예 → 간단하게 시작하고 싶다? → Lightsail
          │
          └── 아니오 → 컨테이너 기반? → ECS (EC2 유형)
                        │
                        └── 아니오 → EC2 (인스턴스 타입 선택)
```

## 🚀 Conclusion

AWS는 단순히 서버 하나를 제공하는 서비스가 아닙니다.
**컴퓨팅 + 네트워크 + 저장소 + 보안이 레이어 단위로 결합된 종합 인프라 플랫폼**입니다.

이 글에서 다룬 내용을 구조적으로 이해하면:

- 어떤 상황에서 EC2를 쓰고, Lambda를 쓸지 판단할 수 있고
- 데이터 손실 없이 인스턴스를 관리할 수 있으며
- VPC를 설계해서 보안을 강화할 수 있습니다.

다음 단계로는 **AWS 콘솔에서 직접 EC2를 생성하고, VPC를 구성하고, Lambda 함수를 배포**해 보는 것을 추천합니다.
이론과 실습이 함께 쌓일 때 AWS 개념은 비로소 진짜 내 것이 됩니다.
